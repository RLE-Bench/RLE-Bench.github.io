Introducing RLE-Bench

A qualifying exam for coding agents working as robot learning engineers. Eight families of real engineering work, sixty-four tasks, every one of them handed to the agent inside a container and graded by a verifier the agent never sees.

Coding agents are now good enough that the interesting question has moved. It is no longer whether one can write a function that passes a test; it is whether one can be handed a piece of engineering work — ambiguous, budgeted, physical, judged by whether the thing actually works — and come back with something you would ship.

RLE-Bench is our attempt to ask that question about robotics. It is not a puzzle set and not a QA set. It is eight families of the work a robot learning engineer actually does: design a mobile manipulator from stock parts, co-design teleop hardware, learn a policy through a metered simulator, build a harness a stranger can use, estimate pose under adversarial sensing, ship a closed-loop controller, reason about physical structure, train a whole-body tracking pipeline.

What ships today

The suite is eight families — task01–task06, task08 and task09 — expanding to 64 individual tasks once every variant is counted. Each family is a self-contained problem with its own container image, its own agent budget, its own verifier, and its own ranking on this site.

Alongside the tasks, the release includes the verifiers, the container images, an Oracle reference solution per family — a human-written submission, published on the leaderboard as an unranked calibration row — and the scoring definitions this site renders from.

How it is scored

Every family produces a continuous score in [0, 1], aggregated from its splits the way its verifier does: the mean of the splits for seven families, and the minimum for task 01, whose one submitted base has to survive all three canonical arms.

The RLE Index is then the unweighted mean of the eight family scores, on a 0–100 scale. Equal weights are the point: with eight families at 12.5 index points each, no model can buy the index with one strong dimension, and the fastest route up is always whichever family it is worst at.

The leaderboard also offers the index by task rank — a model's mean placement across the eight families rather than its mean score. The two orderings disagree, and the disagreement is the interesting part: mean score asks by how much a model wins, mean rank asks how often.

Cost sits on its own axis rather than inside the score. The cost section plots the index against API spend for one complete pass over every family and variant, and each family tab plots that family's score against its share of the bill.

What is deliberately missing

The current release is honest about three gaps, and each one is visible on the site rather than buried.

  • The published scores are placeholders. Task metadata — budgets, splits, reward weights — is read from the benchmark repo and is accurate. The per-model numbers exist so the page renders, and the orange banner at the top of the leaderboard says so. They will be replaced with real aggregates, and the banner will go away at the same moment.
  • Task 09 is only partly calibrated. Of its five motions, only the dance thresholds are calibrated; the other four inherit them and carry a calibrated = false flag. An uncalibrated threshold is not a wrong result, it is a result with unknown units, and the flag is there so readers can weigh it accordingly.
  • The paper is not up yet. The arXiv link in the header is greyed out rather than pointing nowhere, and will become live when the preprint is posted.

Two further limits are structural rather than temporary: everything is simulated — no real hardware, no sim-to-real — and nothing in the suite runs longer than a working day, so the failure modes of a long project are out of scope by construction.

On the missing seven

There is no task07. The slot was built and retired during development, and we left the numbering alone rather than closing the gap, so that published results keep pointing at the same tasks. A gap in a sequence gets asked about once; a shifted sequence is a silent bug forever.

Running it

Each family is a container image plus a manifest. The agent gets the brief, the starter code and its own clock; the verifier runs afterwards, unattended, on its own budget, and writes a reward.json. Nothing else crosses between them — the agent receives no feedback from the verifier, no partial grade and no second attempt. 

git clone https://github.com/RLE-Bench/RLE-Bench-dev
cd RLE-Bench-dev

# build and run one family end to end
rle build task03
rle run   task03 --agent <your-harness> --variant kitchen-07 --level L2
rle score task03            # → reward.json

Family scores land as reward.json aggregates. This site reads a single data.js; publishing a new set of results means replacing the scores block and flipping meta.dataStatus away from "placeholder".

What comes next

In rough order: real scored runs across the frontier models and the open-weight field, replacing the placeholder data; calibrated thresholds for the four remaining task 09 motions; the preprint; and a submission path so that results from harnesses we did not run ourselves can land on the leaderboard under a stated protocol.

We expect the hardest band of task 04 — doors and enclosed cavities — to stay uncleared for a while, and we consider that a feature. A benchmark whose top band is already solved has stopped measuring anything, and you usually find out about it a year late.

More is coming here: the design notes underneath the summary above — how the eight families were chosen, how the verifiers are built, and what building the suite taught us. In the meantime, issues, corrections and disagreements are welcome on the repo.

Budgets, variant counts, split structure and reward weights quoted here are read from the benchmark repo. No per-model scores appear in this post — the leaderboard data is placeholder until real runs land.
